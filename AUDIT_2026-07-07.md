## First: why your reviews kept getting cancelled

This is almost certainly **not** a content flag. Auditing your own coral app is an ordinary task and nothing here trips a safety rule. What likely happened is mechanical: the project is large (the app folder alone is ~1.7 GB, with a 1.2 GB `node_modules` and three ONNX model files of 74–100 MB each), and a review that tries to read those binaries or walk `node_modules` will exhaust the context window or time out mid-run. From your side, "ran out of room and stopped" and "got flagged" look identical.

The workaround I used, and would suggest for future passes: scope the review to text — source, docs, configs, git metadata — and never open the `.onnx`, `.keras`, `.pages`, `.tar.gz`, or `node_modules` files directly. That kept the whole audit inside one clean pass.

---

## Executive summary

The project is genuinely impressive in scope: a working PWA with client-side inference, a Firebase community backend, a batch-scanning workflow, an educational coral guide, and two ML tracks (health + species). It's deployed and functional.

The main risks are not in the app's UX — they're in **provenance, consistency, and data hygiene**. Four documents describe four different versions of the model, the current model work is sitting uncommitted on a feature branch, the original v1 training notebook was lost, and the Firebase database is world-writable. None of these are hard to fix, but they compound: the longer they sit, the harder the project is to hand to a collaborator (e.g. the UVI team) or to reproduce for a publication.

## Findings

### 1. The docs disagree about what the model actually is (highest priority)

There are four sources of truth and they contradict each other:

- **README.md** — describes a **binary** Healthy/Bleached model, "v1.2".
- **PROJECT-SUMMARY.md** — describes v2 as a planned **single 3-class softmax** (Healthy / Unhealthy / Not Coral).
- **MODEL_DEVELOPMENT.md** — describes v2 as a trained single 3-class softmax at 74.6% val accuracy.
- **App.js (actual shipped code)** — implements neither. It runs a **two-stage pipeline**: a `coral_gate.onnx` (coral vs not-coral softmax) followed by `coral_model.onnx` (a *binary* sigmoid for healthy/bleached). This is the "Option A / gatekeeper" design the docs described as the *long-term* future — but it's what's in the working tree right now on branch `feat/v3c-3class`.

So the code has moved past every document. Anyone reading the docs — including you in six months, or a UVI collaborator — will build the wrong mental model. **Pick the v3c gate+binary design as the canonical one, then reconcile all four docs to it and delete or archive the v2-single-softmax narrative.**

### 2. Current model work is uncommitted and partly untracked (risk of loss)

On branch `feat/v3c-3class`:

- `public/coral_model.onnx` — modified, uncommitted
- `src/App.js`, `src/BatchScanner.jsx` — modified, uncommitted
- `public/coral_gate.onnx` (100 MB) — **untracked entirely**

The gate model is the linchpin of the new architecture and git doesn't know it exists. If this machine has a problem, the v3c work is gone. Commit it (or push the branch) — and decide whether 74–100 MB ONNX files belong in git at all (see #6).

### 3. v1 training notebook was lost; architecture was reverse-engineered

MODEL_DEVELOPMENT records that the original v1 notebook couldn't be found (it was in `.gitignore`), so the architecture was reconstructed by inspecting the ONNX file. You recovered it later from a Windows machine, but the underlying problem remains: **`*.ipynb` is gitignored**, so none of your training notebooks are version-controlled. For a project aiming at a Spring 2027 publication, non-reproducible training is a real liability. Remove the blanket `*.ipynb` ignore and commit the notebooks (strip outputs if size is a concern).

### 4. Firebase database is world-writable

Per PROJECT-SUMMARY, the security rules are: read = public, create = anyone (anonymous auth), update/delete = authenticated. That means **any person on the internet can write unlimited observations and upload images** to your Firestore + Storage. The `.gitignore` comment correctly notes the API key being public is fine — that's true and not the issue. The issue is the permissive *write* rules: they invite spam, junk data, and storage-cost abuse, and there's no rules file in the repo to review or version. Add `firestore.rules` / `storage.rules` to the repo, and tighten writes (size limits, rate limiting via App Check, field validation, image size caps).

### 5. Accuracy is below the stated research-grade targets, and it's data-bound

- Health v2: 74.6% (target ≥80%); v1 was 80.8% binary.
- Species: 78.5% with TTA (target 85%).

Your own experiment log reaches the right conclusion: **the ceiling is data-driven, not model-driven** — seven training-side experiments all matched or hurt the baseline. The species weak spots (great star, mustard hill, lettuce, elliptical star) and the health weak spot (bleached recall 67%, plus a `not_coral` class trained on only ~370 images) are all data problems. Effort is better spent on targeted collection and label cleanup than on more architecture tuning.

### 6. Repo hygiene and structure

- **App repo is ~1.7 GB.** Scratch artifacts live in the app root that don't belong there: `download_coral_images.py`, `download_not_coral_images.py`, `download_not_coral_round2.py`, `train_v2_health_model.py`, `train_v3e.log`, `firebase-files.tar.gz`, two `.pages` files (~7 MB). The Python/ML scripts belong in `reef-monitor-ml`; the rest is clutter.
- **Three ONNX files totalling ~248 MB** are tracked in git. Every model revision bloats history permanently. Consider Git LFS or storing models outside git with a documented fetch step.
- **ML repo git state is messy:** `models/best_model.keras` and several JSONs show as **deleted** (tracked but removed on disk), while the new `models/run_20260209_105148/`, `docs/`, `README.md`, and `SESSION_ARCHIVE_20260209.md` are **untracked**. The repo doesn't currently reflect a coherent state — commit the reorganization.
- **`app from old machine/`** sits at the top level of `~/AI` — a duplicate of the project from a prior machine. Confirm nothing unique lives there, then archive it off the working tree.

### 7. Branch sprawl / unclear canonical line

Four branches: `main`, `feature/species`, `feature/v2-health-model`, `feat/v3c-3class`. `main` is what's deployed (binary), but the live production interpretation logic and the v3c working tree have diverged. `v2` and `v3c` represent two *different* model architectures (single softmax vs gate+binary) developed in parallel. Decide which is dead, delete or tag it, and document the decision so the branch list tells a story instead of hiding one.

### 8. Data lives outside the repos with no documented backup

All training data (`~/Data/coral/`, ~10 K images plus a 2.9 GB ReefNet CSV) is correctly kept out of git, but the docs describe it living on a single machine (with references to recovery "from the Windows machine" — suggesting a past near-loss). There's no stated backup or checksum strategy. For publication-track data, document where the canonical copy lives and how it's backed up.

## Path forward — recommended order

The sequencing matters: **stop the bleeding (loss risks) first, then correctness, then quality.**

1. **Commit / push the v3c branch now** — including `coral_gate.onnx`. Stop carrying uncommitted model work. *(minutes)*
2. **Lock down Firebase writes** — add versioned rules files, cap image size, add App Check. This is a live, exposed backend. *(hours)*
3. **Pick one canonical model design (v3c gate+binary) and reconcile all four docs** to match reality. Retire the contradictory v2 narrative. *(hours)*
4. **Un-ignore and commit notebooks**; establish that training is reproducible from the repo. *(hours)*
5. **Clean the repos** — move ML scripts out of the app root, resolve the ML repo's deleted/untracked limbo, decide on Git LFS for `.onnx`, archive `app from old machine/`. *(half day)*
6. **Document the data's canonical location + backup.** *(short)*
7. **Then, and only then, chase accuracy** — targeted `not_coral` and weak-species data collection plus label cleanup, since your own logs show the gains are in data, not architecture. This is also the natural place for the UVI collaboration to plug in (local USVI unhealthy-coral imagery). *(ongoing)*

Items 1–4 are the ones that protect work you've already done. Everything after is improvement rather than insurance.
